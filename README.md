# AtletID: внешний мониторинг production/VPS

Независимый монитор работает на GitHub-hosted runner, вне VPS и Yandex Cloud.
Раз в пять минут (минуты 2, 7, 12 и т. д., UTC) проверяет
`https://atletid.ru/api/health`: требуется HTTPS с корректным сертификатом,
HTTP 200 и JSON с логическим `ok: true`. При неудаче повторяет через 20 секунд;
timeout каждого запроса — 12 секунд. Перенаправление не считается здоровьем.
Ошибка HTTP, DNS, TLS, недоступный Nginx/приложение или выключенный VPS дают тревогу.

Уведомления идут только владельцу в существующий личный Telegram через
`@AtletIDBot`. Токен и chat_id находятся в Actions Secrets
`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Код, git, состояние и логи не содержат
доступа к VPS, S3, базе, документам или токенам. Репозиторий содержит только
код мониторинга и публичный статус. Dev не проверяется: старый адрес health
возвращает 404 и не свидетельствует об отключении production VPS.

Один переход в сбой даёт одно сообщение; восстановление — ещё одно. Первый
успешный запуск и неизменное состояние молчат. Две неудачные попытки уже в первом
запуске дают тревогу. Очередь уведомлений и подтверждённые Telegram message_id
хранятся в `state.json` отдельной ветки `monitor-state`; переменные репозитория
и PAT для работающего монитора не нужны. GitHub выдаёт временный GITHUB_TOKEN
с единственным разрешением contents:write в этом отдельном репозитории.

Событие и попытка сохраняются до отправки; подтверждение — после неё.
Неудачные доставки повторяются с паузами 1/5/15/30 минут (на следующем запуске),
с учётом Telegram retry_after. Подтверждённое сообщение повторно не отправляется.
Если Telegram принял запрос, но ответ или запись подтверждения потерялись,
редкий дубль возможен: у sendMessage нет ключа идемпотентности.
Остаток очереди делает workflow неуспешным, чтобы сбой самого канала был виден
в GitHub. Последующий плановый запуск продолжает доставку в порядке событий.

Workflow сериализован через concurrency, новые запуски не отменяют выполняющийся.
Состояние меняется через Contents API с проверкой SHA; при ошибке записи
уведомление не отправляется. Ежесуточная запись состояния поддерживает активность
репозитория, чтобы не попасть под отключение расписаний публичных репозиториев
после 60 дней без активности. История подтверждённых уведомлений ограничена
100 событиями; идентификатор активационного теста остаётся в состоянии.

Ручной запуск: Actions → External VPS monitor → Run workflow → mode=monitor.
mode=self-test выполняет обычную проверку и один раз отправляет два явно
помеченных тестовых сообщения об условном сбое и восстановлении. Реальный VPS
не выключается, production-состояние не подменяется. Повторный self-test не
дублирует подтверждённые сообщения активационного теста.

Проверки: `python -m unittest -v test_monitor.py`.

Ограничения: расписание GitHub Actions работает best-effort — возможны задержки
и пропуски при нагрузке. Пять минут не являются SLA доставки. При недоступности
самого GitHub или Telegram канал не обеспечивает немедленное сообщение.
Монитор проверяет фактическую внешнюю доступность production, а не состояние
питания ВМ; ошибка сети, DNS или приложения также требует внимания.
